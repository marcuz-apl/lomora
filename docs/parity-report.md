# Part 2 — How part 1 was produced

- Python reference: system `python main.py` on `:8501` (the checked-in `.venv` is an empty
  scaffold, ruling R6), started fresh so its in-memory history is empty.
- Rust: `PORT=8502 LOMORA_DB=/tmp/parity-rs.db cargo run` on `:8502`, fresh database.
- Mock upstream: `cargo run --bin mock_upstream 8600` on `:8600`, so both servers talk to the
  same deterministic upstream (fixed 20 completion tokens, SSE frame split mid-line).
- `cargo test --test parity -- --ignored` drove identical requests at both servers and compared
  parsed JSON (float formatting cannot create a false diff) plus the ordered key/type shape.

# Part 3 — Live smoke, static UI, resources

## Live model run: `gemma4:12b` on Ollama `:11434`

Rust, controlled cold start (model unloaded with `keep_alive: 0` first):

```
{"timestamp":"21:12:47","model":"gemma4:12b","max_tokens":16,"ttft_ms":38760.0,
 "total_s":4.62,"tokens":16,"tok_per_s":3.5}
```

Warm Rust runs were `ttft_ms` 1.9-2.2 s, `total_s` 4.65-4.85 s, `tokens` 16, `tok_per_s`
3.3-3.4. Python, measured while the same model load was in flight, answered
`ttft_ms` 41986.1, `total_s` 5.86, `tokens` 16, `tok_per_s` 2.7.

- Both answered all seven keys, `tokens = 16 > 0`, non-zero throughput, so spec deviation 6
  (a missing `usage` block yielding 0 tokens) was not exercised.
- The very first Rust cold request answered
  `{"error":"TTFT probe failed: error sending request for url (…:11434/v1/chat/completions)"}`
  while Ollama was loading the model. Retries and a controlled unload → cold run succeeded,
  so this is recorded as a transient upstream connection reset during a cold load, not a
  reproducible defect. Python's cold call did not hit it.
- Latencies are not comparable across implementations by design: Python builds a new
  `httpx.AsyncClient` per request, the port reuses one pooled client, and the two runs differ
  in warm/cold state. Success counts, token counts and shape are the parity evidence.

# Part 4 — Known deviations

Spec section 9, unchanged and confirmed: history/profile persistence across restart; one
shared client instead of per-request clients; non-blocking hardware reads; error-detail prose
(spec 1); `profile.cpu` wording (spec 2); `profile.os` composition (spec 3); a background
`cpu_percent` window (spec 4); GPU 0 only (spec 5); `usage.completion_tokens` read with a
default of 0 (spec 6).

Additional differences found while building the parity harness, all deliberate and pinned:

- **`json_invalid` `ctx.error` wording.** Pydantic echoes CPython `json`: "Expecting property
  name enclosed in double quotes". serde_json says "key must be a string at line 1 column 3".
  `type`, `loc` (including the character offset), `msg` and `input` are byte-identical.
- **Unknown-path 404 body.** Python answers `{"detail":"Not Found"}` (FastAPI's handler);
  this port answers plain text `not found`. The dashboard never requests an unknown path.
- **Non-object 2xx body on `/api/models`.** Python's `data.get("data", [])` raises and
  answers `{"error": …}`; the port answers `[]`. Both render as "no models" in the UI.
- **Non-2xx on `/api/models`.** Same 200 `{"error"}` shape; the message is
  `"500 Internal Server Error"` where httpx adds "Server error … for url …".
- **`gpu_error` wording.** The trait reports a failed query generically
  (`"NVML query failed"`) instead of interpolating the NVML exception text.
- **`OLLAMA_URL`.** Applied as the `base_url`-omitted fallback (explicit `LMSTUDIO_URL`, then
  explicit `OLLAMA_URL`, then `localhost:1234`). With the unchanged dashboard, which always
  sends `base_url`, no visible behaviour changes — but the variable is no longer dead.
- Previously recorded: non-string model ids are dropped; a duplicate `base_url` query
  parameter answers axum's plain-text 400 where FastAPI reads the last one; logical cores fall
  back to 1 where Python emits `null` (unreachable on any supported platform);
  `static/index.html` prints "Profile saved" regardless of the response body (frontend out of
  scope); reqwest follows redirects where httpx does not; a JSON `null`/float `usage` is
  handled as 0 tokens where Python would 500 or emit a float; `aiter_lines` splits on a lone
  `\r` where `SseScanner` splits only on `\n`.
